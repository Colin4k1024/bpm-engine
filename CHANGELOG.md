### Added

- **Approval, pause & cancel semantics (E5-2, issue #24 / ADR-008)**: Engine-owned, non-forgeable approval for high-risk steps plus instance-level pause/resume/cancel, with only-once effects under concurrency and retries. **Approvals are persisted engine state, not task variables**: new core types `ApprovalRecord` / `ApprovalStatus` / `ApprovalDecision` (`crates/core/src/approval.rs`, pure), a new `ApprovalStore` storage trait (`create` idempotent by subject `(instance, node, token)`, atomic `decide` — only the first call flips a Pending record, every later call returns the ORIGINAL outcome as `AlreadyDecided`), implemented by the memory adapter and the new Postgres `PostgresApprovalStore` (migration **`0004_approval_records.sql`**: subject-unique `approval_record` table, conditional `UPDATE ... WHERE status = 'Pending'`). **Task-creation-after-approval** (the central design decision): when a token arrives at an approval-required external task (task type in the new `engine.approval_required_task_types` config — TOML array or comma string, default empty = pre-E5-2 behavior), the engine persists a Pending record and the token WAITS; no external task row exists until an operator approves — workers never see unapproved work, so `fetch-and-lock` needs no approval filtering (no TOCTOU). On approve, the engine creates the task **with the engine-written `__approval="true"` task variable** — the E3-3 worker-side gate now reads engine truth on gated types (the `docs/tool-security.md` §3.1 forgeability caveat is closed for them; a client-supplied `__approval` is overwritten by the engine, and un-gated types keep the E3-3 convention so the ai-reference E3-4/E6-3 suites are untouched). On reject, the step is dead-lettered (`approval rejected by <actor>: <note>`), the token terminates (`TokenFailed` recorded) and the instance keeps running its other branches (the E3-2 permanent-failure pattern). **REST**: `POST /api/v1/approvals/:approval_id/decide` `{decision, note?}` (operator), `GET /api/v1/process-instances/:id/approvals` (read), `POST /api/v1/process-instances/:id/pause|resume|cancel` (operator; pause suspends all non-terminal tokens — the core token state machine gains the operator-forced transitions — while the instance state stays RUNNING and in-flight leases deliberately continue; complete/fail/user-task-complete are refused with 409 `instance_paused` until resume; cancel reuses the TerminateEnd family and rejects task ops with 409 `instance_cancelled`). **Only-once** (key acceptance): same-decision retries replay 200 with the recorded outcome, conflicting decisions answer 409 `approval_already_decided`, double pause/cancel are idempotent replays, and concurrent decide/cancel races produce exactly one effect — the atomic store decide plus a process-wide lifecycle mutex serializing pause/resume/cancel (single-service; multi-replica conditional updates documented as out of scope). **History explains the flow**: route-layer events `ApprovalCreated` / `ApprovalGranted` / `ApprovalRejected` / `InstancePaused` / `InstanceResumed` / `InstanceCancelled` carry the verified actor; no new `EngineEvent` variants (approvals are route-layer operations, and replay deliberately models gated steps as immediate task creation). **Error codes**: `approval_not_found` (404), `approval_already_decided`, `instance_paused`, `instance_cancelled`, `instance_not_pausable` (409) — registered in `routes::error_codes`, `docs/openapi.yaml`, and the regenerated agent tool catalog (5 new tools, 31 codes). **RBAC**: decide/pause/resume/cancel are operator actions; the approval list is a read (all roles) — `docs/rbac.md` matrix updated. **Tests**: 4 runtime gate tests, 4 memory ApprovalStore tests, a Postgres Docker integration test, and the new REST suite `crates/server/rest/tests/approval_semantics.rs` (11 tests: approve flow with `__approval` derivation, reject → DLQ + token termination, only-once double/concurrent decide, pause → 409 on complete → resume → completion, cancel → task ops rejected + concurrent cancels one effect, RBAC/tenancy/typed errors). **Docs**: ADR-008 (the decision record), `docs/approval-semantics.md` (the user-side reference with the only-once table), `docs/tool-security.md` §3.1 updated to the engine-truth contract.
- **MCP Server Adapter (E4-2, issue #20)**: New crate `bpm-engine-mcp-server` (`crates/mcp-server`, workspace member, binary `bpm-engine-mcp-server`) — a **Model Context Protocol server over stdio** (newline-delimited JSON-RPC 2.0) that exposes the engine's agent tool surface to MCP clients (Claude Desktop/Code, Cursor, …), dispatching every tool call as ONE authenticated REST call against `BPM_BASE_URL`. **No runtime dependency on any engine crate** (tokio/serde/serde_json/reqwest/anyhow only; `bpm-engine-server-rest` is a dev-dependency for the in-process test server). **Catalog-driven tool surface**: the server embeds the E4-1 agent tool catalog via a workspace-relative `include_str!` of `crates/server/rest/capabilities/agent-tools.json` — no copy exists, and a lockstep test compares the embedded bytes with the server crate's file (disk) and its own embed byte-for-byte; tool names, input schemas (`inputSchema` = the catalog parameters FLATTENED: path/query params + merged object-body properties as top-level properties, raw bodies like deploy's BPMN XML as a single `body` string property, `additionalProperties: false`), descriptions, and `readOnlyHint` annotations all derive mechanically from the catalog, so a regenerated catalog needs no code change. **Workspace-internal by design** (`publish = false` in the crate manifest): the workspace-relative `include_str!` escapes the crate directory, so `cargo package` cannot package it — the single-source catalog embedding IS the feature, and a standalone build would need a build-time copy of the catalog (documented as out of scope). **The v1 surface (decided, 20 of 35 tools)**: validate, dry-run, list definitions, list definition versions, list/get instance, instance history, instance steps, task list, dead-letter list/get, capabilities (read-only, the DEFAULT exposure) plus deploy, start-instance, fetch-and-lock, complete/fail/extend-lock, user-task complete, dead-letter requeue (mutating, opt-in) — enforced STRUCTURALLY (`McpServer::new` refuses any name outside `allowlist::V1_SURFACE`). **Minimal permission (按最小权限授权)**: the server only exposes allowlisted tools — default = the 12 read-only tools; mutating tools require `BPM_MCP_ROLE` (auditor/deployer/operator/worker presets mirroring the E5-1 role→permission matrix) or an explicit `BPM_MCP_ALLOWED_TOOLS` list (role ∩ explicit = pure down-scope); typos and out-of-surface names abort startup with the valid names listed (fail closed). **Tenant validation (校验租户) — the boundary sits engine-side**: the server forwards ONE pre-provisioned credential (`BPM_MCP_TOKEN` bearer JWT, preferred; or legacy `BPM_MCP_API_KEY`; open mode with neither, local dev only) and NEVER sets `X-Tenant-Id` — header parameters are excluded from the input schemas and unknown arguments are rejected, so an MCP client cannot smuggle a tenant or any other header (the one deliberate exception: `Idempotency-Key`, exposed as `start_process_instance`'s optional `idempotency_key` argument for the E2-4 replay); tenancy and RBAC are verified ENGINE-side from the credential's claims (E5-1), and the engine's 401/403/404 bodies surface verbatim in tool results. **Cleartext-credential guard (fail closed)**: a configured credential plus a NON-loopback `http://` base URL refuses startup with a clear error naming the remedies (an `https://` base URL, a loopback host, or the explicit `BPM_MCP_ALLOW_INSECURE_HTTP=1` opt-in — exactly `1`, any other value does not override — which admits the combination with a single stderr warning); `https://` anywhere and plaintext loopback (`localhost` and the loopback IP ranges) are always allowed; open mode (no credential) is unaffected. **Protocol**: `initialize` (version negotiation — a known client version is echoed, unknown/newer gets the latest supported of 2024-11-05/2025-03-26/2025-06-18; capabilities, serverInfo, instructions), `notifications/initialized` (and all notifications — silent, checked BEFORE any validation so even a notification with a wrong `jsonrpc` version is never answered, per JSON-RPC's MUST-NOT-reply rule), `tools/list`, `tools/call`, `ping`; robustness: malformed lines → `-32700` and the loop keeps reading, non-object/batch/wrong-jsonrpc/missing-method → `-32600`, unknown method → `-32601`, unknown tool and invalid arguments (unknown keys, missing required, type/enum mismatches — all pre-I/O) → `-32602`, dispatch breakage → `-32603`; ids echoed verbatim (string|number|null); engine errors are TOOL results with `isError: true` carrying the engine's JSON error body (stable `code`), never protocol errors; timeouts (default 10 s, `BPM_MCP_TIMEOUT_MS`) and transport failures become tool errors, never hangs; 8 MiB message bound ENFORCED AT THE READ LAYER (chunk-by-chunk bounded reading, memory capped at the bound + one 64 KiB reader chunk: an undelimited frame past the limit answers exactly ONE `-32700` oversized-frame error and the stream closes — a client streaming bytes without newlines cannot grow memory without bound; a frame arriving WITH its newline but over the limit is answered `-32600` and the loop keeps reading — the handler-level bound kept as defense in depth; invalid-UTF-8 frames answer `-32700` and the loop keeps reading); stdin EOF and stdout broken-pipe exit cleanly; responses are single-line compact JSON; messages processed sequentially in arrival order (v1 does not abort in-flight calls on `notifications/cancelled`); no secrets logged and proxies are disabled on the HTTP client (credentials must not ride an ambient `HTTP_PROXY`, loopback must not be intercepted). Documented deviations: the per-request-metadata/`server/discover` MCP era (2026-07-28+), server-initiated requests, resources/prompts/sampling, and HTTP transports are v2 scope. **Tests (65 — no external MCP client needed: the request handler is an I/O-free struct with an injected `ToolCaller`, the read loop is stream-generic (`run_over`), and the real binary is spawned via `CARGO_BIN_EXE_…`)**: 26 unit tests (catalog parse/operation split, flattening incl. tenant-header exclusion and `idempotency_key`, argument validation incl. the smuggling guard, request building incl. path-traversal percent-encoding and raw-XML bodies, allowlist resolution matrix + fail-closed, cleartext-guard host/scheme classification); `tests/catalog_lockstep.rs` (4); `tests/protocol.rs` (19 — handshake, tools/list shape, dispatch via a fake caller, error mapping, notification-silence-before-validation, garbage-line fuzz, CRLF/blank/oversized tolerance); `tests/stdio.rs` (4 — the REAL read/write loop over in-process duplex pipes: session ordering with silent notifications, malformed and invalid-UTF-8 frames keeping the loop alive, the partial line at EOF still answered, the clean EOF exit, and the bounded read — an undelimited overrun past 8 MiB answers exactly one `-32700` and stops cleanly, while a delimited over-limit line is answered `-32600` with the loop continuing); `tests/stdio_process.rs` (2 — the actual `bpm-engine-mcp-server` BINARY over real OS pipes against a real `build_app` engine: a full session (handshake, a silent notification, `tools/list`, a real `tools/call` returning engine data, a malformed line mid-session → `-32700` then the loop continuing), closing stdin and asserting the clean exit 0 (the EOF path), plus streaming ~9 MiB without a newline and asserting the process answers one `-32700` oversized-frame line and terminates cleanly — the end-to-end proof of the read-layer bound); `tests/end_to_end.rs` (4 — **MCP → JSON-RPC → REST → engine over a real `build_app` memory-mode server on an ephemeral port**: the full workflow of validate clean/compile-errors-as-200-data/400-tool-error, definition list/versions, idempotent start + replay, instance get/history/steps, task list, fetch-and-lock, complete, final COMPLETED instance, and capabilities; the default allowlist hiding mutating tools (not listed + call → `-32602`); engine-side RBAC 403 `forbidden` for a worker-role token, cross-tenant 404 `not_found`, garbage-token 401 `invalid_token` — all surfacing as tool errors with the engine body; an unreachable engine as a tool error); `tests/env_config.rs` (6 — env parsing, token-over-key precedence, timeout fallback, allowlist end-to-end, and the cleartext-credential fail-closed matrix incl. the `BPM_MCP_ALLOW_INSECURE_HTTP=1` override). **Docs**: new `docs/mcp-server.md` (protocol coverage, env table, permission model with the resolution table, the tenant-enforcement boundary, argument flattening/dispatch, client wiring example, security notes, honest v2 list). No changes to any other crate (the parallel agents own server/rest, core, runtime, storage, adapters — consumed read-only) or to the REST wire contract.
- **Offline Regression Evaluation (E6-3, issue #28)**: New `eval` module in `bpm-engine-ai-reference` (`crates/ai-reference/src/eval.rs`) — a fixed sample set + mock provider harness that compares **definition versions** on success rate, recovery correctness, human-intervention rate, latency and cost, with the **statistical metrics strictly separated from the deterministic kernel tests** (统计指标与确定性内核测试分开). **The separation mechanism**: the DETERMINISTIC invariants live as ordinary tests — `crates/ai-reference/tests/regression_eval.rs` runs a small fast subset (3 cases + the crash-redelivery case, × both versions) through the REAL harness (`run_regression_with` over a self-spawned server + real SDK workers + the offline mock provider) and asserts exact completion states, exact attempt counts, exact costs per the mock price table (18/7/8 µUSD routes), recovery-correctness verdicts, intervention counts and the report's structural validity (both versions present, fields non-negative, serde JSON round-trip, v1-vs-v2 delta fields exist) — while the STATISTICAL/comparative output is a runnable harness, `cargo run -p bpm-engine-ai-reference --example regression_eval` (`crates/ai-reference/examples/regression_eval.rs`, self-contained: spawns the engine on an ephemeral loopback port, deploys both versions, runs the full 13-case set, writes `regression-report.json` and prints a markdown summary), which **asserts nothing**: wall-clock latency and the aggregate rates are reported only — no test asserts a wall-clock performance number (a single generous <5000 ms liveness bound in the deterministic suite guards against hangs, not performance). **Case model**: `RegressionCase { name, flow (FlowSpec: DSL + start variables + user decisions), expectations: CaseExpectations { must_complete, expected_terminal_nodes }, inject: Option<Injection> }` over `Injection = TransientFailOnce | PermanentFail | CrashAndRedeliver` applied by a worker-side `InjectingHandler` wrapping the real `ReferenceHandler` on the flow's first service task — transient fails once with an E3-2 transient category then succeeds on the engine's redelivered attempt; permanent fails straight to Failed+DLQ (no retry storm); crash sleeps past the lease with no renewal and returns a stale result whose submission the engine rejects (exactly the E3-2 crash semantics: lease expiry → reclaim → redelivery, no retry consumed). **The fixed case set** (`fixed_case_set()`, 13 cases from the five reference flows): retrieval baseline + the three recovery injections; inference low/high risk; approval approved/unapproved; tool approved/transient-failure/unapproved; compensation happy/failed — where `tool-transient-failure` is the deliberate behavior-changing probe. **Definition versions**: `fixture_version_selector()` maps each case's v1 (the flow as-is) to a v2 *fixture variant* registered under a `:2`-suffixed definition id (honest scoping — the versions are fixture variants in the harness, that IS the comparison mechanism; instance start resolves definitions by exact id so both coexist): retrieval +`validate` step after the summary, inference gateway default flipped (behavior-preserving refactor by design), approval +`validate` step before the side effect, tool **`retries: 3 → 1`** (behavior-changing: the single transient failure then exhausts the budget → blocked + DLQ, surfaced as the success-rate/recovery delta), compensation +`audit` step after undo; a new plain `ref-validate` task type dispatches in the reference handler; unknown def ids fall back to the identity mapping (documented). **The report** (`RegressionReport`, serde round-trip-pinned): per case × version `CaseRun` (completed, terminal_nodes, steps, attempts, failed_attempts, latency_ms [reported only], cost_micros/tokens from the E6-1 envelope summaries, intervention_points, decision_points, dlq_entry, `RecoveryVerdict`, expectation_met), per-version `VersionSummary` (success_rate, recovery_rate, intervention_rate, cost/step/attempt/token totals, latency mean/min/max) and a `VersionComparison` (rate/cost/step/attempt/latency deltas + per-case `CaseDelta`), plus `markdown_summary()` for humans; recovery-correctness rules and intervention counting (user-task decisions + `__approval` inputs over declared decisions + side-effect gates) are pure deterministic functions pinned by unit tests. **Timing honesty**: the eval profile (`eval_flow_options()`: 2 s lease, 200 ms worker poll) uses 2 s rather than 1 s because the store's lease expiry is second-granular — a 1 s lease is a 0–1000 ms true lease and plain tasks could expire mid-handle collecting phantom attempts; blocked cases exit their driver early on the instance's dead-letter entry (in this engine a DLQ'd task leaves the instance terminally blocked). **Plumbing** (all inside `crates/ai-reference`, read-only consumers elsewhere): `FlowOptions` gains a `lock_duration` field + builder (default keeps the historical 30 s; the runner's worker config now uses it), the runner's internal REST client/outcome snapshot become crate-visible for the eval driver, and `FlowOptions::worker_poll_interval` feeds the eval worker. **Tests**: 18 new unit tests (case-set/fixture/selector invariants, all five v2 DSLs compile, injection targeting, recovery-rule tables, aggregation math incl. empty sets and delta computation, report JSON round-trip, markdown content, intervention counting, the injection hook against a dead endpoint) + the 2-test deterministic integration suite (stable across repeated runs; parallel-test env-var isolation). **Docs**: new `docs/regression-eval.md` (the case set, metric definitions incl. what counts as an intervention and how recovery correctness is judged, latency = wall-clock reported-only with step/attempt proxies, the v1/v2 fixture-version mechanism, how to run, the separation principle, extension guide); `regression-report.json` gitignored. No changes to `crates/core`, `crates/worker-sdk`, `crates/runtime`, `crates/server/rest` (the parallel E6 agent owns the server crate) or the REST wire contract.
- **Identity Binding & RBAC (E5-1, issue #23)**: `/api/v1` requests are now identified by **verified credentials** and authorized by a role→permission matrix, replacing the untrusted `X-Tenant-Id` header as the tenant source. **JWT identity**: when `auth.jwt_secret` (`BPM_AUTH__JWT_SECRET` / `BPM_JWT_SECRET`) is configured, every `/api/v1` request must carry `Authorization: Bearer <jwt>` (HS256, claims `{ sub: actor, tenant, role, exp [, iat] }`, strict zero-leeway expiry); the new `authenticate` middleware (`crates/server/rest/src/middleware.rs`, replacing `api_key_auth` at the same layer position) verifies signature/claims, inserts a typed `Identity` into request extensions, and answers failures with the new stable 401 `invalid_token`. **Mode precedence**: a presented JWT always wins; without one, the legacy admin `X-API-Key` (`BPM_API_KEY`) is the documented full-access bootstrap fallback (401 `unauthorized` on a presented-but-invalid key); with neither secret configured the server stays in open mode (byte-identical pre-E5-1 behavior, `X-Tenant-Id` unchanged as a dev-mode affordance). **RBAC** (middleware, before handlers, 403 `forbidden` = new stable code): deployer — deploy/activate/deprecate definitions; operator — start instances, complete user tasks, replay sessions, DLQ requeue+delete; worker — the external-task lease lifecycle ONLY (fetch-and-lock/complete/fail/extend-lock; operators administrate via the DLQ by design); auditor — the read-only role; every GET and the side-effect-free POSTs validate/dry-run are allowed for ALL authenticated roles; the admin API key bypasses role checks; the table is fail-closed and drift-guarded by a unit test over `routes::registered_routes()`. **X-Tenant-Id deprecation**: under JWT the tenant comes from the verified claim — an absent/agreeing header is accepted, a CONFLICTING header answers 403 `forbidden`. **Cross-tenant isolation** (key acceptance): listings are claim-scoped; instance-scoped reads/writes (get/trace/history/steps/task-form/task-complete/replay-create) of another tenant answer 404 `not_found` with the exact body an unknown id produces (no existence leak); external-task complete/fail/extend-lock on another tenant's task answer the unknown-task 400 `task_not_found` BEFORE any state changes; replay sessions are bound to the creating tenant; dead letters inherit the failing worker's claim tenant at insert (open/API-key inserts stay untagged) with list/get/requeue/delete gates. **Worker fetch tenancy decision**: `ExternalTaskStore` gains `fetch_and_lock_scoped(worker, types, max, lock, tenant_id)` — the tenant check runs INSIDE the atomic select-and-lock section (memory: instance-tenant filter in the critical section; Postgres: the `FOR UPDATE SKIP LOCKED` selection joins `process_instance.tenant_id`), so another tenant's task is never delivered AND never leased (filtering results after an unscoped fetch would silently steal the lease); the unscoped `fetch_and_lock` (open/API-key/admin) is unchanged. Actor identity is part of the request context and request logs (persisting it into history is E5-3's audit trail, deliberately not done here). **Token minting**: new example `crates/server/rest/examples/mint_jwt.rs` (`cargo run -p bpm-engine-server-rest --example mint_jwt -- --sub <actor> --tenant <tenant> --role <role> [--exp | --exp-in]`, reads `BPM_JWT_SECRET`) plus the programmatic `middleware::mint_jwt` helper used by the tests. **Contract**: `docs/openapi.yaml` gains the `BearerAuth` security scheme (http/bearer/JWT) alongside `ApiKeyAuth` (global security: either satisfies), 403 `Forbidden` on every `/api/v1` operation, the `invalid_token`/`forbidden` codes in the `ErrorResponse` enum, the deprecated-`X-Tenant-Id` parameter note, and updated `AgentToolsAuth` (type/scheme/bearerFormat/schemes) / `AgentToolsConventions` (new `roles` matrix) schemas; the agent tool catalog was regenerated (auth block describes the three modes + precedence + deprecation; `conventions.roles` carries the matrix; two new error examples) — lockstep green. **Tests**: new `crates/server/rest/tests/rbac.rs` (10 REST-level tests, own process with the fixed test secret + admin key, memory mode): JWT enforcement (missing/garbage/wrong-secret/expired/non-bearer → 401 `invalid_token`, wrong API key → 401 `unauthorized`, health/capabilities stay open), one matrix test per role (allowed AND denied representative endpoints), cross-tenant isolation (indistinguishable-from-unknown 404s incl. byte-shape equality, claim-scoped listings, user-task complete, replay sessions), worker fetch tenancy (tenant B gets nothing and never steals the lease; cross-tenant complete/fail/extend = unknown-task 400), dead-letter tenancy (permanent fail → tenant-tagged entry; other tenant cannot list/get/requeue/delete), conflicting-tenant-header 403, and the API-key full-access bootstrap path (X-Tenant-Id honored, JWT precedence). Middleware unit tests: role parse, mint/verify round-trip, bad claims, bearer parsing, the permission-table drift guard, and matrix spot checks; memory-adapter store test for the scoped fetch. **Docs**: new `docs/rbac.md` (modes, claims, minting, matrix with decisions, tenant isolation incl. the worker-fetch decision, X-Tenant-Id deprecation, E5-3 boundary); `docs/api-spec.md` error-code table + `AuthConfig` doc comments updated. Backward compatibility: open mode is byte-identical (all pre-existing suites green); API-key mode keeps 401 `unauthorized` and full access; no wire field removed — the catalog additions are additive.
- **AI Reference Flows & Model-Provider Adapter Layer (E3-4, issue #18)**: New crate `bpm-engine-ai-reference` (`crates/ai-reference`, workspace member) — the reference implementation of the five AI workflow shapes plus the swappable model-provider layer they run against, fully offline by default. **Provider adapter layer**: `#[async_trait] ModelProvider { async fn generate(ModelRequest) -> Result<ModelResponse> }` with `ModelRequest { prompt, variables: HashMap<String,String>, max_tokens }` / `ModelResponse { text, tokens_in, tokens_out }`; `max_tokens` clamps the output count; no randomness, no clock); `UnconfiguredProvider` is the always-compiled stub failing with a clear `provider_unconfigured:` error naming the options; `OpenAiCompatProvider` (new cargo feature `http`, **off by default** — enables TLS) speaks the OpenAI-compatible chat-completions wire format with env-only config (`OPENAI_BASE_URL`/`OPENAI_API_KEY`/`OPENAI_MODEL`, read exactly once at `from_env()` construction, never during generate) so applications can swap providers while the reference suite always uses the mock. **Cost helper**: `ProviderConfig` (identity + per-model price table, mock default 250/500 micro-USD per 1k in/out tokens) maps every `ModelResponse` onto the E3-1 envelope `TaskCost` with integer math (`amount_micros = (in*in_price + out*out_price)/1000` — the three mock routes cost exactly 18/7/8 micro-USD, assertable in CI; `duration_ms` stays `None`, no clock); wired into envelopes via `FlowOptions::pricing`. **The five flows** (DSL v1 JSON documents stored inline as `pub const` — `RETRIEVAL_DSL`…`COMPENSATION_DSL` — plus `FlowSpec` constructors): 检索 `retrieval_flow` (retrieve → summarize(model) → end: a model task over a plain task's chained output, envelope with model+cost in `/steps`); 工具 `tool_flow(memo, approved)` (the E3-3 boundary end to end: allowlist deny-by-default, approval gate, `CredentialSource::env` credentials with missing-env → permanent `credential_missing` naming the var never a value, output masking/limits via `TaskOutput::add_tool_output`, tool recorded in the envelope); 补偿 `compensation_flow(fail)` (reserve → charge → gateway: failure path routes to an `undo` step compensating the completed forward steps in REVERSE order — the engine's saga shape; happy path ships). **SagaCoordinator** (`saga.rs`): the application-side compensation loop over the engine's `CompensationRecordRepo` (record → list → Pending → newest-first undo → stop at first failure), honest to v1's append-only trait (outcomes reported, not written back); ### Fixed

- **EL boolean splitting inside quoted literals (E2-1 review finding)**: `eval_condition` split on ` or ` / ` and ` before checking whether the separator was inside a single/double-quoted string literal, so conditions like `x == "salt and pepper"` silently mis-evaluated (splitting the quoted literal into boolean operands). Splitting is now quote-aware (`split_outside_quotes`, with regression tests). This affects both BPMN `<conditionExpression>` and DSL `variableEq` lowering, restoring the exact-string-equality equivalence claimed by ADR-006.
- **Timer Intermediate Catch Misfire (E1-3 finding)**: `TokenArrivedHandler` marked the token `Waiting` at a `timerIntermediateCatchEvent` but never persisted a `TimerRecord`, so instances waiting on a timer catch never advanced (the scheduler had nothing to fire). The handler now schedules the persistent timer (ADR-004) when the token arrives, using the same `list_due`/`TimerFired` path as boundary timers.
- **PostgreSQL `ExternalTaskStore::complete` lock-expiry gap (E1-3 finding)**: unlike the memory adapter, complete did not check `lock_expire_at`, so a worker whose lease had expired (but was not yet reclaimed) could still complete the task. It now runs in a transaction (`SELECT ... FOR UPDATE`) and returns the same typed errors as memory (`TaskNotFound` / `TaskNotLocked` / `ExternalTaskLeaseConflict` / `LockExpired`), all mapped to HTTP 400.
- **PostgreSQL `external_task.updated_at` mixed formats**: `complete`/`fail` wrote `CURRENT_TIMESTAMP` into the TEXT column while `create`/`extend_lock` wrote unix-epoch seconds. Unified on TEXT unix-epoch seconds.
- **Postgres migrate()**: `idx_token_state_updated` referenced the nonexistent `token(state)` column (the column is `status`), so every migration failed; all postgres integration tests were blocked by this.
- **Postgres ProcessStore::load**: SELECT did not include `parent_instance_id`/`parent_token_id` but read them, panicking on every load.
- **Postgres ExternalTaskStore**: parameter type mismatches (`i64` vs `int4`) and mixed timestamp conventions (`to_timestamp`/`CURRENT_TIMESTAMP` vs TEXT epoch seconds) broke create/fetch-and-lock/reclaim; unified on TEXT unix-epoch seconds like the memory adapter.

## [0.1.0] - First formal commitment

**What is stable**

- Process-instances, history, trace, and external-task APIs, and their semantics (docs/api-spec.md §8, §9).
- History/Trace: append-only events, globally ordered per instance, deterministic replay, persistence-first.
- Invariant violation response: `X-Invariant-Violation` header and error body contract.

**What is NOT stable / may evolve**

- Replay API (session/step/seek), UI/Inspector, SDK helper interfaces, and future Python SDK may be extended or adjusted; they do not affect the stable set above.

**What users can rely on**

- The stable APIs and semantics above will not receive breaking changes within minor/patch versions.
- History is auditable and replayable; causal order and persistence-first are design commitments.

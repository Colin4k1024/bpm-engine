# 🧩 三、External Task 的「分布式生命周期」

你现在可以把它升级为 **Lease-Based Task Execution**

```
READY
  │ fetch & lock (lease)
  ▼
LOCKED (lease_expire_at)
  │ heartbeat / extend
  │
  ├─ complete → DONE
  ├─ fail     → READY / FAILED
  └─ timeout  → READY
```

---

# 🔒 四、Lease / Lock 设计（非常关键）

## ExternalTask 核心字段（你应该已经有）

```text
state
lock_owner
lock_expire_at
retries
```

### 再强调一次语义：

- **lock_owner = worker_id**
- **lock_expire_at = now + ttl**
- 任何操作必须校验这两个字段

---

## Fetch & Lock（原子）

```sql
UPDATE external_tasks
SET
  state = 'LOCKED',
  lock_owner = :worker_id,
  lock_expire_at = now() + :ttl
WHERE task_id IN (
  SELECT task_id
  FROM external_tasks
  WHERE state = 'READY'
  ORDER BY created_at
  LIMIT :n
)
RETURNING *;
```

✔ 多 Worker 天然竞争
✔ 不需要分布式锁

# 🔁 六、Fail / Retry 的「分布式正确语义」

## Fail 不等于失败

### Fail 的真实含义

> **“我这次没跑完”**

---

## Engine 行为（唯一正确的）

```text
retries -= 1

if retries > 0:
  state = READY
  schedule retry_after
else:
  state = FAILED
  token = FAILED
  trigger saga
```

⚠️ Worker **不应该知道 retries 具体策略**

---

# 🔂 七、幂等性（你必须防的真实事故）

## 问题场景（一定会发生）

- Worker 调 complete → 网络超时
- Worker retry complete
- Engine 已处理过

---

## 正确做法（非常重要）

### Complete / Fail 必须是幂等的

```text
if task.state != LOCKED:
  return OK (no-op)
```

👉 **不要返回 error**
👉 Worker 不需要知道“是不是第一次”

---

# 🔥 八、Crash Recovery（Engine 侧）

## Engine Scheduler 必须周期性做：

```sql
UPDATE external_tasks
SET
  state = 'READY',
  lock_owner = NULL,
  lock_expire_at = NULL
WHERE
  state = 'LOCKED'
  AND lock_expire_at < now();
```

这一步 = **Worker crash 自动恢复**

# 🔀 九、并发场景下的正确性保证

## 同一个 Task 被两个 Worker 执行？

> **不可能成功写入**

因为：

- 所有写操作都校验 lock_owner
- DB 行级锁

---

## Join / Parallel 情况下

- 一个分支卡住
- Join 永远等它
- TTL 到期 → retry → 正确恢复

✔ 和 BPMN 语义一致
